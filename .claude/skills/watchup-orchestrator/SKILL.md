# Universal Core — Skill Discovery and Selection

## Purpose

Every orchestrator must discover available skills, build capability records from
file content, and select the minimum relevant set for the current task. Skill
selection must be evidence-based: folder names alone are never sufficient.

## Skill Discovery

### Mandatory Recursive Inventory

1. Resolve the project root.
2. Enter the project's skill directory (e.g. `.claude/skills/`, `.agents/skills/`,
   or the path specified in the orchestrator's configuration).
3. Recursively enumerate every directory and every file, including hidden files
   when the filesystem tool supports them.
4. Record per file: relative path, type/extension, size, parent skill folder,
   and whether content is readable.
5. Detect top-level and nested `SKILL.md` files, missing `SKILL.md`, duplicate
   declared names, folder/frontmatter mismatches, broken relative references,
   wrappers, generated artifacts, and invalid packages.
6. Read any optional local policy/catalog (e.g. `SKILLS_POLICY.md`) as an
   overlay only. Live disk content remains authoritative.
7. Include matching globals (e.g. user-level skill directories) only when the
   project's policy explicitly references them; never double-count a skill ID.

### Metadata-First Pass (token governance)

Selection is two-stage. Reading every file of every skill is forbidden: a
project skill corpus can exceed any context window (WEBTOPKIDS: 3.6 MB).

Stage 1 — metadata only, for every skill folder:

- Read the `SKILL.md` frontmatter (`name`, `description`, triggers, exclusions)
  and at most the first 40 lines of the body.
- Record file count and total size from the inventory. Do not open
  references, scripts, assets or data files in this stage.
- Build a compact capability record:

```
declared_id
folder
description_and_triggers
exclusions
size_and_file_count
task_relevance
validity
```

Stage 2 — full content, only for the selected skills (at most 3 per agent):

- Read the selected `SKILL.md` completely, and only the references it names
  that the current task needs.
- Read scripts only to learn inputs, outputs, side effects and safety
  constraints. Do not execute scripts during discovery.
- Never expose secrets or private runtime data; record only a sanitized risk
  note.
- Pass the selected skill paths to the worker contract. Do not paste skill
  bodies into every worker. Release the skill after the task.

### Coverage Integrity

The scan is incomplete unless:

- Every top-level skill folder has a metadata record or an invalid-package
  record.
- Every selected skill had a Stage 2 read, or the failure is recorded.
- Selection happens only after the Stage 1 pass over the whole inventory.

If a selected skill cannot be read, continue when safe but mark the scan as
`warning`. If an unreadable file prevents reliable selection of a critical
skill, the orchestrator must stop and report the block.

### Scan Universe

1. **PRIMARY:** every top-level directory under the project's skill root.
2. **OPTIONAL:** catalog IDs from the project's local skills policy.
3. **OPTIONAL:** policy-referenced installed globals, without double-counting.

TOTAL = the live unique on-disk skill count for this project only.

Per scanned skill, classify internally:
`selected | supporting | not_relevant | installed_global | catalog_only_missing | invalid | duplicated`

## Evidence-Based Selection

After the complete recursive content scan, match the user's prompt and
constraints against each capability record.

Do not maintain or trust a static topic-to-skill table: installed skills,
identifiers, bundled resources, and project needs change. Route only from the
capability records built by the current scan.

Before scoring, extract requested outcomes, affected systems, languages, data
types, integrations, safety boundaries, and explicit exclusions from the
current user prompt.

### Selection Priority

1. Explicit user-named skills that are valid and applicable.
2. Project-specific skills with direct evidence for the affected files or
   systems.
3. Integration/domain skills whose triggers and resources match the task.
4. Validators required by the selected work.
5. Generic supporting skills only when they add a capability not already covered.

### Selection Rules

1. Score capability records by direct trigger match, reusable implementation
   assets, project specificity, required validation, and risk constraints.
2. Prefer the smallest set that fully covers the task. Avoid duplicate skills
   that provide the same capability.
3. Treat folder names and catalog categories only as navigation hints; cite
   file-content evidence for every selection.
4. Apply all safety constraints discovered inside selected skills.
5. If an expected capability is absent, say so. Never invent, borrow from
   another project, or silently substitute a similarly named skill.
6. For each selected skill, retain at least one evidence path and one sentence
   explaining the match.
7. Mark overlaps and choose the smallest non-duplicative set.

### Output Contract

The orchestrator must report:

1. The selection ratio: `N of TOTAL` (where N = skills activated for this task,
   TOTAL = live unique count for this project).
2. Selected skills only: name, short reason, evidence path.
3. Do not list not-selected / skipped / near-miss skill names in default output.
   Keep that filtering internal.
4. Always include: `Selection basis: full recursive content analysis; folder
   names were not used as sole evidence`.

## Hard Rules

- TOTAL is the live unique count for this project only.
- Disk folders absent from a policy table still count and are selectable.
- Catalog IDs with no on-disk `SKILL.md` count as `catalog_only_missing`.
- Every readable file is scanned before selection; only selected/supporting
  skill details are carried forward into execution context.
- Folder names may help navigation but must never be the sole selection reason.
- If a selected skill is missing, invalid, or unreadable and critical, the
  orchestrator must stop.
- Skill counts and contents change per project. Never hardcode totals, reuse
  another project's inventory, trust a stale policy table, or infer a
  capability only from a folder name.

# Universal Core — Task Classification

## Purpose

Every orchestrator must classify incoming tasks before planning. Classification
drives skill selection, validation intensity, model routing, and risk assessment.

## Taxonomy

Classify every task as exactly one primary label. Add a secondary label in notes
only when the task genuinely spans two domains.

| ID | Label |
|---|---|
| 1 | audit only |
| 2 | bug fix |
| 3 | feature implementation |
| 4 | UI/UX improvement |
| 5 | dashboard change |
| 6 | agent pipeline change |
| 7 | n8n workflow change |
| 8 | deployment/VPS task |
| 9 | documentation update |
| 10 | research task |
| 11 | resume/job matching improvement |
| 12 | data integrity task |
| 13 | security/safety task |
| 14 | Gmail/email task |
| 15 | Telegram task |
| 16 | Google Sheets task |
| 17 | prompt/skill creation task |
| 18 | production verification task |

Labels that do not apply to a given project may still be used when the task
matches; unused domains are simply never selected.

## Required Internal Notes

After classification, the orchestrator must also determine:

- complexity (low / medium / high)
- risk (low / medium / high)
- dependencies (none, or list of affected systems/files)

These inform downstream decisions (skill selection, model routing, validation
intensity) but are not part of the user-facing classification output.

## Rules

1. Classification must happen during preflight, before planning begins.
2. The primary label drives the default `Task:` line in orchestrator output.
3. Classification is based on the user's stated goal and the orchestrator's
   understanding of the project's systems — not on skill availability.
4. A task may have only one primary label. Multi-domain tasks use the dominant
   domain as primary and note the secondary internally.
5. The taxonomy is extensible: project-specific orchestrators may define
   additional labels in their configuration, but the base 18 must always be
   available.

# Universal Core — Phased Planning

## Purpose

Every orchestrator must decompose work into phases, assign compute profiles to
each phase, present the full plan before execution, and gate phase transitions.

## Phase Compute Profile

Every phase must declare:

| Field | Values |
|---|---|
| Model | A real model name — never an abstract tier like `fast` / `medium` / `advanced` |
| Reasoning | `low` / `medium` / `high` / `deep` |
| Thinking | `on` / `off` (extended thinking — always stated explicitly, never inferred from Reasoning) |
| Estimated cost | `low` / `medium` / `high` |
| Depends | `none` / reference to prior phase(s) |
| Parallel | `no` / `yes` / `yes-with-<phase>` |
| Deliverable | one line — what this phase actually produces |

If a phase plan omits Model + Reasoning + Thinking + Depends/Parallel +
Deliverable, the plan is invalid and must be corrected before approval.

### Model Naming

The orchestrator must name actual models, not abstract tiers. The reference set
(from the current Dream Team ecosystem) is:

| Model | Typical use |
|---|---|
| Haiku | copy edits, renames, docs typos, mechanical single-file work |
| Sonnet | ordinary multi-file work, UI, tests, straightforward bug fixes |
| Opus | architecture, security, pipeline/scoring, deploy, deep audits, production-risk |
| Fable | only when the user explicitly requests it |

Project-specific orchestrators may define a different model vocabulary in their
configuration. The principle remains: name real models, not tiers.

**Token rule:** prefer the cheapest model + reasoning that can safely accomplish
the phase. Never recommend the most capable model for trivial work.

### Existing compute heuristic

This table documents the current default mapping used by reference
orchestrators. It is not an adaptive, learned, or telemetry-driven router.

| Phase shape | Reference model | Reasoning | Thinking |
|---|---|---|---|
| Copy/docs, renames, mechanical single-file edits | cheapest capable (reference: Haiku) | low | off |
| Single-file bug | cheapest capable (reference: Haiku) | medium | off |
| Ordinary multi-file work, UI, tests, straightforward bug fixes | balanced (reference: Sonnet) | (no new default) | off |
| Architecture, security, pipeline/scoring, deploy, deep audit, production-risk | most capable (reference: Opus) | high or deep | on |

`Parallel: yes` only for disjoint file sets with no shared state, no
runtime-orchestrator risk, and no deploy risk. If unsure, `Parallel: no`.

### Thinking On/Off

Every phase must state whether extended thinking is `on` or `off`. Default
heuristic (override when the task clearly calls for the other):

| Phase shape | Thinking |
|---|---|
| Copy/docs, renames, mechanical single-file edits | off |
| Ordinary multi-file work, UI, routine bug fixes | off |
| Architecture, security, scoring/matching logic, root-cause debugging, expensive-if-wrong decisions | on |
| Deploy/production verification | on if the decision is judgment-heavy, otherwise off |

## Full Plan First

Before the first phase is approved, the orchestrator must present the entire
plan — every phase, in order, each with its compute profile and deliverable.
The user must never be asked to approve Phase 1 while later phases are only
names without details.

## Session-Grouping Statement

Every full plan and every between-phase gate must include a plain-language
paragraph (in the user's language) that states the actual execution grouping
as a human would say it:

- Which phases must run together in the same session (and why: shared files,
  shared state, sequential edits to the same module).
- Which phases can run in parallel (and why: fully disjoint files, no overlap).
- Which phases must wait for another to finish (and what they wait for).

Every phase must be named at least once. This paragraph comes before the
per-phase compute-profile lines.

## Phase Approval Gate

The orchestrator must never execute all phases continuously. After presenting
the plan, it stops and waits for explicit Phase 1 approval.

No commit, push, deploy, or git-add suggestions inside the preflight output.

## Execute Approved Phase Only

Run only the approved phase. On completion:

- If more phases remain: present the between-phase gate (re-print remaining
  plan with deliverables, updated session-grouping statement, next phase
  compute profile, and wait for approval).
- If this was the last phase: proceed to validation, documentation check, and
  final report.

## Between-Phase Gate

When Phase N finishes and phases remain, the orchestrator must output:

1. One-line result of the completed phase.
2. Count and list of remaining phases (name + deliverable, one line each).
3. Updated session-grouping statement for remaining phases.
4. Next phase compute profile (Model, Reasoning, Thinking, Cost, Depends,
   Parallel).
5. Wait for approval.

If no phases remain, skip the between-phase gate and proceed to final report.

## Final Report

After the last phase, the orchestrator must produce a structured final report
containing:

- Project root
- Task classification
- Files inspected
- Skills scanned and used (N of TOTAL)
- Files changed
- Files skipped due to conflict risk
- Tests/checks run
- Git status summary
- Validation result (if applicable)
- Human approvals requested
- Risks/limitations
- Documentation updated
- What was not tested
- Recommended next step
- Phases executed with actual Model/Reasoning/Thinking used

## Optional Phases

Phases that are not required for the core task but may add value should be
marked `OPTIONAL — separate approval` in the plan. Optional phases are never
executed automatically; they require explicit approval.

# Universal Core — Human-in-the-Loop / Protected Actions

## Purpose

Define the universal set of actions that always require explicit human (owner)
approval before execution, regardless of execution mode. This list is the
safety foundation for all orchestrators.

## Protected Action List

Stop and request explicit approval before:

- each execution phase
- commit
- push
- deploy
- delete
- dirty file overwrite
- live scan / production mutations
- scoring / matching policy changes (when the project has them)
- runtime-orchestrator state machine changes (when present)
- Gmail send / auto-send / auto-apply
- browser automation / login automation / CAPTCHA handling
- n8n activation
- secrets / `.env`
- VPS / production configuration changes
- database / Google Sheets schema or write/update
- authentication / permission changes
- protected scraping
- destructive shell commands

Also stop at every between-phase gate.

## Rules

1. This list applies identically in MANUAL and AUTONOMOUS_SAFE mode.
   AUTONOMOUS_SAFE changes only the inter-phase approval gate for a routine,
   non-protected phase — it never removes any item on this list.

2. Every protected action stops until the owner explicitly approves the exact
   action and target. No agent can delegate or infer this approval.

3. Protected actions are never included in any worker's tool allowlist and are
   never dispatched to a worker — they always stop in the main session,
   regardless of mode.

4. Project-specific orchestrators may extend this list with additional protected
   actions (via the `protected_actions.additional` field in engine configuration)
   but may never remove items from it.

5. When validation detects that a phase touched a protected action, the
   `owner_approval_required` field must be set to `true` in the verdict,
   regardless of the validation outcome.

## Governance Authority

The owner/final authority (as defined in `governance.json`) is the only entity
that can approve protected actions. The management chain (e.g. Chief of Staff,
orchestrator) cannot delegate or bypass this approval.

# Universal Core — Safety Rules

## Purpose

Define the universal safety hard rules that all orchestrators must enforce
during execution. These rules complement the protected action list (hitl.md)
with operational constraints.

## Hard Rules

- No secrets in code, logs, docs, or commits.
- No `.env` changes unless the user explicitly requested them.
- No auto-apply / auto-send / Gmail send / CAPTCHA / login / browser automation
  without approval.
- No protected scraping.
- No deploy / push / commit without approval.
- No unrelated refactors; no "fix everything" scope expansion.
- Never use more skills than necessary.
- Never omit Model / Reasoning / Thinking / Parallel from a phase plan or
  next-phase gate.
- Never expose credentials (including Google Sheets / Gmail OAuth tokens).

## Extension

Project-specific orchestrators may add project-specific safety rules but must
never weaken or remove any rule from this list.

# Universal Core — Execution Mode

## Purpose

Define the universal execution modes available to orchestrators and the rules
governing transitions between them.

## Modes

### MANUAL (default)

- Default whenever Mode is not explicitly set.
- The existing human approval gate, between-phase gate, safety hard rules, and
  permanent rules remain authoritative.
- The orchestrator stops at every phase boundary and waits for explicit approval.

### AUTONOMOUS_SAFE

- Activated only by an explicit phrase from the user or the owner authority.
  Never self-activates from task size or phrasing alone.
- The activation phrase is defined by the project-specific orchestrator
  configuration (e.g. trigger words with an "autonomous" qualifier).
- **Environment restriction (v1):** AUTONOMOUS_SAFE is available in Claude Code
  only. In Codex, Cursor, or any other tool, AUTONOMOUS_SAFE must not activate.
  The orchestrator reports the restriction and continues in MANUAL mode.
- **Protected actions always stop, in both modes.** Every item in the
  protected-action list (hitl.md) always requires explicit owner approval.
  AUTONOMOUS_SAFE changes only the inter-phase approval gate for a routine,
  non-protected phase — it never removes a protected-action stop.
- **Max retry per phase: 3 attempts.** A 4th attempt never happens
  automatically. See the repair loop (repair-loop.md).
- **Validation verdict controls phase progression** in both modes:
  - PASS: continue.
  - WARNING: continue automatically only if the phase touched no protected
    action and the validator's `owner_approval_required` is false; otherwise
    stop, exactly like a protected action.
  - BLOCKED: repair/retry per the repair loop, or escalate once attempts are
    exhausted.
- When AUTONOMOUS_SAFE is active, every phase transition still triggers a
  continuity checkpoint (goal, phase, task, next_action, files_touched,
  last_worker) so state is never lost even without a human pause.

## Rules

1. Mode selection must be explicit. The orchestrator never infers AUTONOMOUS_SAFE
   from task complexity, length, or phrasing.
2. The owner can always override the mode at any point.
3. Mode applies per-objective, not per-phase. Switching mode mid-objective
   requires explicit owner instruction.
4. Provider capabilities may restrict which modes are available. The orchestrator
   must respect provider limitations and never advertise unavailable modes.

# Universal Core — Worker Dispatch Contract

## Purpose

Define the universal contract for dispatching work to subagents/workers in
AUTONOMOUS_SAFE mode. In MANUAL mode, this section is not consulted.

## Dispatch Record

Each phase additionally declares, before dispatch:

| Field | Value |
|---|---|
| Worker | Identifier of the worker to dispatch (from the Dream Team workers or project-specific workers) |
| Tools | The worker's own fixed tool allowlist (not chosen per-phase) |
| Model / Effort | Worker frontmatter default, unless the phase plan states an explicit override (see precedence below) |
| Attempt | 1 / 2 / 3 |
| Max attempts | 3 |
| Validation | Validator required/not-required + intensity (LITE/STANDARD/DEEP) |
| Restrictions | Preflight restrictions + any phase-specific restrictions |

## Dispatch Protocol

1. Read the worker's canonical definition to determine its tool allowlist,
   default model, and default effort level.
2. Pass the phase's exact objective, scope, and any skills it needs. Workers
   have no native `skills:` field, so required skills are named explicitly in
   the dispatch prompt, using the same evidence-backed selection already
   performed during preflight.
3. Include all relevant restrictions from the preflight and any phase-specific
   constraints.

## Model/Effort Precedence

The worker's own frontmatter (`model:`, `effort:`) is the safe default fallback
and applies unless the phase plan explicitly overrides it.

The orchestrator's phase plan may explicitly set a different Model and/or Effort
for a specific dispatch when the phase's risk/complexity justifies it (e.g.
lowering effort for a trivial phase, or raising it for one that needs deeper
reasoning than the worker's default).

An override must be stated explicitly in that phase's dispatch record — silence
means the frontmatter default is used. Whatever Model/Effort was actually used
for the dispatch (frontmatter default or explicit override) is the value that
must be written to the execution trace, never the frontmatter's nominal default
when an override was in effect.

## Protected Action Boundary

Protected actions (commit, push, deploy, delete, production mutation, secrets,
outbound action) are never included in any worker's tool allowlist and are never
dispatched to a worker — they always stop for the owner in the main session,
regardless of mode.

## Worker Result Contract

On completion, the worker must return a structured result:

| Field | Values |
|---|---|
| status | done / partial / blocked |
| evidence | file:line references |
| files_touched | list of modified files |
| files_created | list of new files |
| files_deleted | list of removed files |
| blocker | description if status is blocked |

Only the orchestrator branches on this structured result. A worker's own
narrative claim of success is not itself evidence; the validator verifies it
whenever validation is required for the phase.

# Universal Core — Repair Loop / Retry / Escalation

## Purpose

Define the universal repair/retry/escalation policy for AUTONOMOUS_SAFE mode.
In MANUAL mode, a BLOCKED result is simply reported and the orchestrator stops
for the user.

## Retry Ladder

```
Attempt 1  Worker = selected, Model/Reasoning/Thinking = selected
   | BLOCKED
Attempt 2  Worker = same, Reasoning +1 tier, instructions refined with validator's required_fix
   | BLOCKED
Attempt 3  Model upgraded OR a specialist worker OR one additional relevant skill/tool
   | BLOCKED
STOP -> escalate to owner. Continuity state: status=blocked, blockers[], next_action.
Never attempt a 4th time automatically.
```

## No-Progress Guard

If two consecutive attempts return the identical `required_fix` from the
validator, stop immediately rather than spending the remaining attempt on a
fix that is not changing.

## WARNING Handling

Continue automatically only when the phase touched no protected action and the
validator's `owner_approval_required` is false.

Any WARNING mentioning secrets, production, or data integrity is treated as a
stop, never an auto-continue, regardless of intensity.

## Loop Ceilings (defence in depth — all independent of each other)

1. **Max attempts: 3 per phase** — tracked from the continuity checkpoint,
   read from disk each time, never from memory.
2. **Worker turn limit** — each worker's own `maxTurns` is platform-enforced
   and cannot be overridden by a dispatch.
3. **Global dispatch ceiling** — a total ceiling on dispatches for the
   objective; on breach, stop and report rather than continuing silently.
   The default ceiling is configurable in the orchestrator's engine
   configuration (`execution_mode.max_total_dispatches`).

## Escalation

When all retry attempts are exhausted:

1. Stop the blocked task immediately.
2. Mark the task as blocked in the continuity checkpoint (status=blocked,
   blockers list, next_action describing what the owner must decide).
3. Report evidence: which attempts were made, what the validator found each
   time, what changed between attempts, and what remained unresolved.
4. Never attempt a 4th automatic repair.

The owner decides the next action: manual fix, architectural change, scope
reduction, or task cancellation.

## Learning Review

After a meaningful NO-GO, repair, or revalidation that reaches GO, the
orchestrator requests a learning review from the existing learning subsystem.
The review names a root cause, whether the failure is likely to recur, whether
equivalent protection already exists, and the smallest prevention to propose.

Prevention priority, smallest first: automated test, validation rule, skill,
shared Core rule, project instruction.

A one-time mistake does not create a reusable rule. Recurring, structural, or
clearly preventable failures may propose a regression test. Changes to policy,
permissions, skills, Core rules, or project instructions stay recommendations
for the existing authority model.

The learning review never validates, never repairs, never overrides a Gate
decision, and never grants the validator write access.

# Universal Core — Execution Telemetry

## Purpose

Define the universal execution trace protocol. The trace is an append-only log
of dispatch and validation transitions, owned by the orchestrator.

## Trace Location

Default path: `.ai/andy/trace.jsonl` (append-only, one JSON object per line).

The path is configurable via the engine configuration (`telemetry.trace_path`).

## Ownership

The trace is owned and written by the orchestrator, not by the continuity system.
It does not read, write, or alter the continuity state file.

## When to Write

The orchestrator appends one record for every:

- Initial worker dispatch
- Retry dispatch
- Validation result
- Protected-action stop (worker = main session, validation = blocked)

This applies in both MANUAL and AUTONOMOUS_SAFE mode.

## Required Fields Per Record

| Field | Description |
|---|---|
| ts | ISO 8601 timestamp |
| objective | Current goal/objective |
| phase | Phase identifier |
| worker | Worker identifier (or "main_session" for protected-action stops) |
| model | Model actually used (not the nominal default if overridden) |
| effort | Reasoning effort actually used |
| skills | Skills provided to the worker |
| tools | Tools available to the worker |
| attempt | Attempt number (starts at 1) |
| files_touched | Files modified by this dispatch |
| validation | Validation result (pass/warning/blocked/pending) |
| required_fix | Fix required by the validator (empty if none) |
| retry_of | Timestamp of the attempt this retries (links attempt 2 to attempt 1) |
| escalated | True only when the retry policy's escalation fired |

## Record Integrity Rules

1. `model` and `effort` must record the values actually used for the dispatch,
   never a nominal default when an override was in effect.
2. `attempt` starts at 1; a retry increments `attempt` and sets `retry_of` to
   the `ts` of the prior attempt.
3. `escalated` is true only when reasoning-tier or model escalation fired.
4. A protected-action stop is also traced: `worker` is `main_session`,
   `validation` is `blocked`, and `required_fix` names the approval needed.

## Implementation

The reference implementation is `uri-orchestrator/core/trace.py` — a standalone
script with no dependency on the continuity system's state helper. It validates
required fields and appends a single JSON line.

## Token, Context & Usage Governance

Goal: maximum useful work per unit of context and usage. Pick the cheapest
capable model and reasoning for the actual task. Numbers come from
`dream-team/policies/governance.json` → `resource_governance` (the only source
of truth). The values below mirror it; a test keeps them in sync.

### Authority stages

Owner input → **Yuli** mission/resource decision (Mission Budget Plan) →
**Ori** orchestration decision (who, when, model class, reasoning, context
packet, iterations, retry, shutdown) → Worker → Valdi → Gate → Andy.
Yuli and Ori may share the main thread, but they stay separate stages: record
Yuli decisions as actor `yuli` and Ori decisions as actor `orchestrator`.
Never spawn Yuli or Ori as subagent threads in a host-native runtime.

### Mission Budget Plan (Yuli, before execution)

Complexity (simple / normal / complex), expected phases, maximum parallelism,
expected specialist roles, default model class, escalation model class,
default reasoning, maximum retries, validation strategy, context policy,
checkpoint strategy, and a work-unit budget (defaults: simple 12, normal 40,
complex 100).

### Concurrency (Ori enforces)

- Default **1**. Normal maximum **2**. Hard maximum **4**. Spawn depth **1**.
- Two concurrent agents only for disjoint scopes where at most one writes.
  Parallel writers stay off.
- More than 2 needs all of: independent tasks, no overlapping files,
  measurable benefit, minimal context duplication, budget GREEN, and a
  justification recorded in the mission audit.
- Release idle agents. Spawn Valdi only when the artifact is ready and release
  it after the verdict.

### Spawn policy (answer before every spawn)

1. Is another agent actually required? 2. Can the current bounded worker finish
this? 3. Is the work independent? 4. Will it duplicate context? 5. Is a
specialist required? 6. Is the model/reasoning justified? 7. What is the stop
condition? No strong justification → **do not spawn**.

### Agent Contract (every dispatch)

Agent, Role, Task, Goal, Files allowed, Files prohibited, Required context,
Maximum context, Expected output, Model class, Reasoning, Maximum iterations,
Maximum retries, Validation requirement, Stop condition. Record MODEL_CLASS,
REASONING and WHY.

### Model and reasoning classes

| Class | Use for | Default reasoning |
|---|---|---|
| FAST | discovery, search, inventory, formatting, mapping, extraction, simple docs | low |
| STANDARD | ordinary implementation, UX, scoped changes, normal bug fixes, ordinary validation | medium |
| HIGH | difficult architecture, non-trivial root cause, security, complex integration, important final gate (reason required) | high |
| ESCALATED | only after a failure with evidence or proven complexity (reason required) | high |

Never inherit HIGH from the parent session. Never default every worker to the
strongest model.

### Agent budgets

| Kind | Class / reasoning | Iterations | Turns | Context tokens | Files |
|---|---|---|---|---|---|
| discovery | FAST / low | 1 | 12 | 6000 | 12 |
| research | FAST / low | 1 | 20 | 6000 | 16 |
| implementation | STANDARD / medium | 2 | 30 | 8000 | 24 |
| validation | STANDARD / medium | 1 (+1 revalidation per repair cycle) | 20 | 8000 | 24 |
| architecture | HIGH / high | 1 | 25 | 10000 | 24 |

### Context

Mission → phase → agent. An agent packet holds the exact task, exact files or
sections, acceptance criteria and current relevant state. It never holds the
full HANDOFF, the full conversation, project history, unrelated architecture,
previous checkpoints or the full Andy `current.json` (the engine compact
previous-state digest is allowed). Host spawns use no forked history
(`fork_turns: none`). Skills: metadata-first, at most 3 loaded per agent,
released after the task.

### Retry and validation

Attempt 1 → classify the failure. Attempt 2 only with a clear corrective
action. Attempt 3 is a **REPLAN**: change at least one of context scope,
specialist, reasoning or model. The same route is never repeated. After the
ceiling the task is BLOCKED for Ori re-planning. Valdi gets requirement,
changed files, relevant tests, evidence and expected DOD. Deterministic checks
run first. HIGH reasoning is only for the final gate, security or
architecture.

### Usage governor states

Effective ratio = max(platform used fraction when available, proxy work-unit
ratio). Always label the telemetry source; never invent platform numbers.

| State | From | Behavior |
|---|---|---|
| GREEN | < 0.50 | normal (max 2 concurrent) |
| YELLOW | 0.50 | no optional parallelism (max 1), reduce context duplication |
| ORANGE | 0.70 | no new optional agents, no model escalation, finish the bounded phase, checkpoint |
| RED | 0.85 | stop spawning, finish only the safe atomic step, Andy checkpoint, return resumable state |

RED is not an Owner escalation (quota exhaustion stays inside the Dream Team).

### Andy checkpoint

Main thread only; at most 6144 bytes. Fields: objective, completed, active,
blocked, changed files, validation state, next exact action, essential
decisions. Never a transcript.
