# README and GitHub Presentation System

## README redesign

The README should read like a premium product landing page that happens to live inside
GitHub. Include, where they genuinely apply: a cinematic hero section, product name,
tagline, short explanation, creator/version credit if provided, a badge row, product
story, feature cards, architecture and workflow diagrams, an AI/automation explanation
if relevant, dashboard and mobile screenshot sections, setup, environment variables,
local development, testing, deployment, roadmap, project structure, and license.

Rules that matter more than the template:
- Don't invent commands — inspect the project first. If a command is genuinely unclear,
  mark it `TODO` rather than guessing.
- Don't present fake screenshots as real; use a clearly-labeled placeholder path if
  screenshots don't exist yet.
- Use Mermaid diagrams where they clarify something, and make sure they're valid.
- Remove duplicate or outdated sections rather than piling new content on top of them.
- Keep it scannable — someone should be able to understand the product in 30 seconds
  and find the setup instructions in under a minute.

## GitHub presentation

Beyond the README itself: badge rules, screenshot rules, diagram rules, feature card
rules, roadmap rules, setup clarity, repo description guidance, social preview image
guidance, and case study / portfolio presentation guidance. The repository as a whole
should read as professional and credible enough to show an investor, a user, a
recruiter, or a potential collaborator without extra explanation.
